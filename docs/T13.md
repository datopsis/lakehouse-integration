## Limits

Static S3 credentials remain private fixture scaffolding; named-table denials
are not arbitrary-path storage isolation. Phase D STS is not qualified. Sail
and direct-client machine identities have no grants on the row/mask table;
Trino's trusted connector identity must load its metadata. A trusted host or
holder of its broad static keys can bypass engine restrictions.

Revocation checks use fresh catalog requests/queries/Spark sessions and old
unexpired human/team tokens. They do not revoke fetched data, already admitted
queries, engine caches or previously issued storage credentials. A supervisor
obtains team tokens; the automatic token-broker role is still unimplemented.

Every evaluated authorization decision requires a committed audit. Transport
rejections before a policy request exists and failure of the audit database
cannot durably record themselves. Gateway decisions are exactly reconciled;
all fixture principals require both permit and deny records, exact row/mask
results are persisted, and the complete audit digest must survive DB restart.
C1–C8 retains the fresh-empty-human-group compatibility gap documented upstream.

## Required-gate duration and immutable image reuse

Moving the whole-stack stage alone cannot remove Rauthy/authz compilation from
Integration because its mandatory C1–C8 stage needs those same images. Both
workflows therefore cache only the expensive native Rauthy/authz image archives,
keyed by full owner source revision, CPU and build-recipe digest. Other image
builds and every runtime assertion continue normally. No cache fallback key is
used. A changed Trino pin does not invalidate unchanged Rauthy/authz builds.

Each hit fetches the exact source again, verifies its repository lock, checks the
archive checksum and exact tag/config digest inventory, then independently
inspects every loaded image's ID, source revision, architecture and artifact-lock
label. Invalid caches fail rather than falling back or receiving an allowance.
Both authz outputs are mandatory. The normal strict provenance gate still runs.
FIDO feed authentication/CRLs/dates are rechecked even when its image is cached.
Caches are saved only after that job's provenance gate succeeds, before runtime
fixtures create secrets. No runtime state, credentials or decision is cached.

Cold misses remain source builds and can exceed the former required-gate
duration. The warm-cache target is roughly the previous duration plus C1–C8;
actual cold/warm durations and this move's branch dispatch are pending CI evidence.
The historical durations above describe the earlier combined workflow only.

## Branch dispatch before workflow registration

GitHub rejected direct branch dispatch of the new workflow with HTTP 404 because
`t13.yml` is not yet on the default branch. Until it is registered, the existing
manual-only evaluation workflow offers a `t13` choice calling the exact same
`t13-native.yml` reusable profile. Its native jobs independently require a
schedule/manual caller, so a pull-request caller cannot run T13. The bridge has
read-only permissions and cannot invoke the schedule-only tracking issue job.

```bash
gh workflow run idp-bakeoff.yml --ref room/lakehouse-integration-mvp-slice-4b-t13-a-ef8i -f suite=t13
```

After merge, `gh workflow run t13.yml --ref <branch>` uses the registered nightly
wrapper directly. No GitHub setting or default-branch content is changed here.

The JWT mapping anchors the whole nonempty subject (`^(.+)$`) before prepending
`oidc~`. Trino uses Java `Matcher.replaceAll`; an unanchored `(.*)` also replaces
the empty suffix and produces an invalid duplicate-prefix principal. The first
new-pin run exposed this as fail-closed OPA 503 responses, never valid denials.
The private `trino-catalog` connector credential is separate from the incoming
least-privilege machine client and can load both team namespaces. Its additional
negative control denies a namespace outside that union. Exact caller/team
allow/deny and audit assertions remain mandatory.
